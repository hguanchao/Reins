## 三、第 4 步：配置解析器验证与部分换库（已完成）

原文计划是「解析器全部换库，动手前验证三件事（错误定位 / 写回保真 / 子集覆盖）」。
2026-10-29 用 `smol-toml` 与 `jsonc-parser` 实测后，结论是只换 JSON 一半：

**JSON：换 `jsonc-parser`（3.3.1，精确锁定）。** 三件事全部通过：

1. 错误定位：库按错误码 + 偏移量报错，偏移经 `offsetToLineColumn` 换算行列，与原报错
   格式一致；库的错误码在 `config/json/parser.ts` 里翻译成人话。
2. 写回保真：`providers.json` 是纯声明、没有任何回写路径（`JsonDocument` 不提供 set），
   不存在保真问题。
3. 子集覆盖：重复键库本身放行，但语法树保留全部属性节点，读取层自己遍历检测并拒绝；
   值树用本项目 `setTableValue` 组装，`__proto__` 仍是普通键；尾随逗号维持拒绝
   （`allowTrailingComma: false`）。原来手写的 275 行解析器降为 224 行的「翻译 + 重建」
   薄层，转义、注释、数字等边界交给库维护。

**TOML：保留手写解析器，不换库。** 用 `smol-toml` 实测三件事，两条不过：

1. 错误定位：`TomlError` 只有行号没有列号，`ConfigError` 的「第几行第几列」会退化。
2. 写回保真：parse + stringify 往返把独立注释与行尾注释全部丢掉。这不是库的实现问题，
   是 TOML 的结构性限制——注释在解析时就丢了，任何库都还原不回来。而 `/model`、信任
   记录等回写依赖手写解析器留下的区间索引做「只替换值那一段」的定点改写，换库必然
   每次写配置都毁掉手写注释。
3. 子集覆盖：我们有意拒绝的日期值被库悄悄放行。

TOML 侧维持「代码不少、依赖不加」的现状，与原文的取舍判断一致：手写解析器的维护负担
没有显形，写回保真是硬约束。运行时依赖净增 1 个（`jsonc-parser`），不是预计的 1–2 个。
