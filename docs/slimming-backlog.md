## 三、第 3 步：统一选择面板（未做）

**现状。** 五个选择面板各有自己的渲染器、状态与处理函数：`panel/model-menu.ts`（116 行）、
`panel/effort-menu.ts`（112 行）、`panel/session-menu.ts`（153 行）、`panel/command-menu.ts`
（104 行）、`panel/file-menu.ts`（206 行），加上共享的 `panel/menu-panel.ts`（148 行）。
`runtime/panels.ts`（542 行）里开关、移动、确认、补全、取消也按面板各写一份。列表行的
排版规则已经共享（`menuListLines` / `keepVisible` / `moveMenuSelection`），重复的是「一个
列表 + 光标 + 滚动窗口」外围的那一圈状态机。

**做法。** 抽一个通用列表菜单：共享状态（items / cursor / scrollTop / hover / pressed）和
列表渲染，每个菜单只保留自己的差异点作为钩子——命令菜单按输入过滤、文件菜单按 `@` 片段
过滤并在确认时插路径、模型与思考等级确认时写回配置、会话菜单有 `f` 分叉。确认与插入
行为留在各自的回调里，不要硬套成一个接口。

**预计。** 源码约省 300–400 行；对应测试也会合并一部分。

**风险。** 中。五个菜单的交互差异是真实的（过滤来源、确认副作用、Tab 语义、鼠标补全），
抽得不好会把简单情形变复杂。必须一次只迁一个面板（先迁最简单的思考等级），每迁一个
跑全量测试。

**判断标准。** 如果做完第一个迁移发现钩子比被省掉的代码还多，就停手——重复但直白的
代码好过抽象但间接的代码。

## 四、第 4 步：配置解析器换库（未做，需要先拍板）

**现状。** 配置解析全部手写：`config/toml/parser.ts`（689 行）、`document.ts`（165 行）、
`serialize.ts`（63 行）、`config/json/parser.ts`（275 行）、`document.ts`（45 行），合计
1,237 行。手写的理由有两个：解析错误要带文件与行列（`ConfigError` 的定位能力），写回时
要保留使用者配置里的注释与排版（`serialize.ts`）。

**候选库。**

- TOML：`smol-toml`（小、ESM、parse + stringify 都有）；`@iarna/toml`（更大，错误信息好）。
- JSON：读取用内置 `JSON.parse`；写回若要保留注释与排版，用 `jsonc-parser` 的编辑 API。

**预计。** 源码约省 700–900 行；运行时依赖增加 1–2 个。

**动手前必须验证的三件事。**

1. 错误定位：库的解析错误能否换算出行与列？不能的话，配置错误的「第几行第几列」体验退化，
   这是现在报错信息的核心。
2. 写回保真：`/model`、信任记录等都会写回配置文件。库的序列化必须保留使用者写的注释与
   排版，否则每次切模型都会毁掉手写配置。
3. 子集覆盖：现在只支持本项目用到的 TOML 构造（简单表、字符串、数字、布尔、数组）。
   换库后反过来要确认：库更宽松的语法会不会让以前报错的配置悄悄通过， aliases
   （camelCase / snake_case）的处理仍留在我们的读取层，不受影响。

**取舍。** 这一步与「运行时更轻」方向相反：代码少了，依赖多了。只有当手写解析器的维护
负担真正显形（出 bug、要补 TOML 特性）时才值得做；否则维持现状。
